# DoggyFeed

A lightweight meal-planning app for tracking food nutrition across multiple dogs, served by Node.js and backed by MariaDB.

## Requirements

Node.js 18 or later and a MariaDB server. Create the `doggyfeed` database and grant the `doggyfeed` user access to it before starting the app.

## Run

```sh
npm install
npm start
```

Place the database settings in `/etc/doggyfeed/doggyfeed.env` before starting the app. Use `.env.example` as the template and restrict access to the file (for example, `chmod 600 /etc/doggyfeed/doggyfeed.env`). The app reads this path before creating its MariaDB connection pool. If that file is missing, for example on Windows, the app falls back to a `.env` file in the project folder (ignored by Git). To use a different env file, set `DOGGYFEED_ENV_FILE`. Open `http://127.0.0.1:3000`. For automatic restarts during development, run `npm run dev`.

After updating DoggyFeed (for example with `git pull`), restart the server. The page is read fresh on every visit, but the server code and database changes only load when the server starts. Until then, saves may not reach the database, and the page shows a "Restart the DoggyFeed server" warning.

If DoggyFeed runs behind a reverse proxy such as nginx, allow request bodies of a few megabytes (for example `client_max_body_size 20m;`) so new dog photos and food pictures can be saved. Pictures already stored are not sent again with later saves. When the app loads, its data carries links to the pictures instead of the pictures themselves, and the browser fetches and caches each picture from `/api/pictures/`.

Open `http://127.0.0.1:3000/diagnostics` to inspect database tables, row counts, columns, and stored values. This read-only page is restricted to requests from the local computer. It shows every dog house's data, but never password hashes or session tokens.

The app stores dog profiles, foods and pictures, meal contents, saved plans, and the selected dog in MariaDB tables. If an existing `data/state.json` file is present and the database has not yet been initialized, its contents are imported once. The database env file and `data/` directory are ignored by Git. Database settings can also be provided through environment variables: `DB_HOST`, `DB_PORT`, `DB_NAME`, `DB_USER`, and `DB_PASSWORD`.

## Dog houses and sign-in

All data belongs to a dog house (table `dog_house`: name, contact, email), and every data table has a `dog_house_id` column. Users sign in with a username and password and only ever see and change their own dog house's dogs, foods, bowls, plans, weight history, calendar and served bowls.

- **First start after updating:** the server moves all existing data into a dog house called "My dog house". Opening DoggyFeed then shows "Set up DoggyFeed", where you name the dog house and create the first user. Back up the database (for example with `mysqldump`) before the first start, as this changes every table.
- **New dog houses:** anyone who can reach DoggyFeed can create a new dog house with its first user from the sign-in screen ("Create a new dog house"). A new dog house starts with sample dogs and foods. This form is protected against abuse:
  - a hidden honeypot field that people never fill in; when a bot does, the server answers as if it worked but creates nothing;
  - a timing check with a signed form token issued when the form opens: a form sent back within 3 seconds, after more than an hour, or with a changed or already used token is refused;
  - a taken username gets the same general answer ("could not be created with these details") as other refused details, so the form cannot be used to find out which usernames exist;
  - hard limits per network address of 5 attempts per hour and 20 per day, and 3 new dog houses per day, plus 50 new dog houses per day in total; over a limit the server answers 429 with a Retry-After time. The limits are kept in memory and reset when the server restarts. Behind a reverse proxy every request comes from the proxy's address; set `DOGGYFEED_TRUST_PROXY=1` to use the first address in `X-Forwarded-For` instead, but only when your proxy always sets that header (sign-in throttling uses the same address).
- **Dog house photo:** the Dog house profile can hold a photo (stored in `dog_house.photo`, shrunk in the browser to at most 1600 px before upload). It is shown behind Estimated energy in the Meal planner instead of the sample picture, and only users of that dog house can load it.
- **Dog house page:** edit the dog house's name, contact and email, add users, set passwords (which signs that user out everywhere else) and remove users. Usernames are unique across all dog houses.
- **Admin console:** administrators see an Admin page with every dog house and user. They can add, edit and delete dog houses (deleting removes the dog house with all its data and users, after typing its name to confirm), and add users to any dog house, set passwords, move users to another dog house, give or remove administrator rights, and delete users. The user who sets up DoggyFeed is the first administrator; on an existing install without an administrator, the oldest user becomes one at server start. Administrators cannot delete or demote themselves or delete their own dog house, and DoggyFeed always keeps at least one administrator.
- **Sign-in protection:** the Sign in form has the same honeypot field and form token as the New dog house form (with a minimum of 1 second instead of 3, as password managers fill the form at once); a filled-in honeypot gets the same answer as a wrong password. A wrong username and a wrong password get the same answer after the same password hashing. Hard limits on failed sign-ins: 5 for one username from one address (then a minute's wait), 10 per address in 15 minutes, 50 per address per day, and 20 per username per hour from all addresses together; over a limit the server answers 429 with a Retry-After time. The limits are kept in memory and use the same address as the New dog house limits (see `DOGGYFEED_TRUST_PROXY`).
- **Security:** passwords are stored only as scrypt hashes. A session lasts 30 days from its last use and is kept in an HttpOnly cookie; the database stores only a hash of the session token. Behind an https proxy, the cookie is marked Secure when the proxy sends `X-Forwarded-Proto: https`.

## Features

- Keep individual dog profiles, weights, desired weights, meals per day, life stages, and activity estimates. The bowl energy reference uses the desired weight when set and is split across the meals per day.
- Keep a weight history: each saved change to a dog's weight or desired weight is stored with its date, and the Weight history view (linked below the dog form) charts the last 12 months.
- Import weight and daily energy history from a CSV file in the Weight history view. The file needs a header row with `date` and `weight`, and may add `desired_weight`, `daily_energy`, and `daily_energy_custom` (yes/no). Dates can be `YYYY-MM-DD` or `DD.MM.YYYY`; comma, semicolon, or tab separators and decimal commas are accepted. A row for a day that already has an entry replaces it. Use the CSV template button for an example.
- Import foods into the food library from a CSV file with the Import CSV button. The file needs a header row with `name` and `kcal`, and may add `category`, `protein`, `fat`, and `fiber` (all per 100 g), `portion` (grams), `stock` (pieces), plus `manufacturer_url` and `shop_url` web links (http or https). A portion, stock or link column left empty clears that value for the food; a file without the column keeps existing values. A row whose name matches a food in the library updates it and keeps its picture; unknown categories become Other. Use the CSV template button for an example.
- Maintain a food library with energy, protein, fat, and fiber values per 100 g, and an optional portion in grams. A food with a portion is added to a bowl with that amount (and adding it again adds another portion), including Dry food, which then is not auto-filled. A food can also have a stock in pieces (leave it empty to not track it): each Bowl served takes off the pieces used for every food that is not Dry food, that is the grams served divided by the food's portion, or one piece for a food without a portion. Stock does not go below 0; a food at 0 is shown in red in the Food library. Stock can be changed directly in the Stock column of the Food library: it is saved when the field loses focus or on Enter (Escape puts the old value back), and an empty field stops tracking the food's stock. Deleting a served bowl from Bowls history does not put stock back. When a food's stock drops below 2 pieces, an event "<food> - out of stock" for all dogs is added to the Dog's calendar automatically, starting at that moment and linking to the food's eShop page; there is at most one per food, and it is removed again once the stock is 2 or more, the stock field is emptied, or the food is deleted.
- Add foods and serving amounts to each dog's bowl to calculate nutrition totals. With more than one dog, Add&sync puts the chosen food into every dog's bowl at once; an auto-filled Dry food is then worked out for each bowl from that dog's own target. Sync bowl replaces every other dog's bowl with a copy of this one: other foods keep their amounts, and Dry food is auto-filled to each dog's kcal per bowl. A food in the "Dry food" category fills the energy the other foods leave below the bowl target, and its amount updates as the bowl changes; typing an amount for it, or using its Auto-fill button, turns this off.
- Keep a Dog's calendar of events for one dog or for all dogs: description, location, start, length, an optional web link, and an optional repeat (every day, week, year, or every chosen number of days). The calendar shows a month at a time with a dog filter and lists the next 30 days; click a day to add an event and an event to change or delete it. Each dog's card in My dogs lists its next three events within 60 days (its own and those for all dogs), with a button to add one. Events are stored in the `calendar_events` table, which the server creates on start. An event can have a reminder 1 day, 1 week, 1 month, or a chosen number of days before it: from then until the event starts, it is listed at the top of every page (with a button to dismiss it; on the Meal planner and My dogs the Reminders ribbon is always shown and, below what is due, lists the next 6 events from tomorrow on within 90 days, each repeating event once), and shown once as a system notification when the browser allows them. The reminders also list every event that starts today, with or without a reminder and also once it has started (these are not sent as notifications unless the event has a reminder). Reminders only appear while DoggyFeed is open, and system notifications need DoggyFeed opened over https or on the server computer itself (`http://127.0.0.1`).
- Record a bowl with Bowl served, and see each dog's served bowls 10 days at a time in Bowls history. Each served bowl in the list can be moved to another date and time with Edit date, or removed with Delete.
- Save a dog's bowl as a meal plan with Save bowl, at the bottom of the bowl, and load it into the bowl again for reuse. A plan is named after the dog and the first food in the bowl (for example "Milo – Chicken kibble"); saving a bowl whose plan name already exists asks to replace that plan.
- Save profiles, foods, and meal plans to MariaDB through the Node server.

The starter foods are sample entries. Verify nutrition values against product labels or a trusted database. The energy reference is a rough estimate, not a feeding prescription or veterinary advice. The server binds to `127.0.0.1` by default; set `HOST` or `PORT` to override it.
